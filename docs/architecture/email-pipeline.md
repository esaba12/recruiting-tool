## Email Pipeline (Google Apps Script)

File: `scripts/email-pipeline.js`
Deploy: script.google.com → paste file → Script Properties → add `ANTHROPIC_API_KEY` + `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` + `RECRUITING_USER_ID` → run `setup()` → add trigger (every 10 min)

**Discovery (fixed 2026-08-10 — see below) → Claude Haiku classifies + extracts (newest message only) → upsert contact in Supabase (`contacts` table) → upsert application (`applications` table) → Google Calendar event (real interviews only, and only when no invite is attached — see below) → every message new since the last run (tracked per-thread via `PropertiesService`, key `msgcount_<threadId>`) gets logged as its own row in `interactions` (no LLM call) → `recruiting-done` label applied as a visual marker only (no longer gates processing, since a thread can grow replies after being marked done).**

**Discovery is three Gmail searches, deduped by thread ID, not just the manually-applied `recruiting` label:** (1) threads already labeled `recruiting`, (2) recent Sent-folder threads not yet labeled (`SENT_SCAN_QUERY`, catches the user's own new cold outreach), and (3) recent Inbox threads not yet labeled that look recruiting-shaped by sender/subject (`INBOX_SCAN_QUERY` — a known ATS domain like `greenhouse.io`/`myworkday.com`/`lever.co`, or a subject containing "application"/"interview"/"offer"/etc.). Source (3) is the fix for the original bug: an inbound "thanks for applying" confirmation that was never manually labeled used to be completely invisible to the script. The keyword list is intentionally broad recall, not a precision filter — Claude's `UNRELATED` classification is the real filter, so a false-positive Gmail match just costs one cheap Haiku call, while a false negative was a silently-missed application.

**Classification recognizes application confirmations, not just replies/invites/offers/rejections:** `type` includes `APPLICATION_CONFIRMATION` (an automated "we received your application" ATS/no-reply acknowledgment, before any human has replied) alongside `REPLY|INTERVIEW_INVITE|OFFER|REJECTION|NEW_CONTACT|FOLLOW_UP_NEEDED`, and `upsertApplication()` now fires on `APPLICATION_CONFIRMATION` too (creating the Pipeline row at stage `Applied` the moment the application lands, not only once a human responds). Cheap deterministic regex hints (`APPLICATION_CONFIRMATION_RE`, a sender-domain company guess via `guessCompanyHint()`) are fed into the Claude prompt the same way the calendar-invite/meeting-link hints already were, to raise recall on a single-shot Haiku call. A `STAGE_RANK` guard on `upsertApplication()` stops a later, fuzzy-company-matched signal from regressing an application's stage backward (e.g. a second, unrelated confirmation email can't knock a `Phone Screen` back down to `Applied`) — `REJECTION` is exempt since it's terminal and can land at any stage.

**Referrer extraction:** the prompt now also asks for `referrer_name` — the name of whoever referred/recommended the candidate, extracted *only* when the email explicitly says so (e.g. "referred by Jane Doe", "submitted your referral"), with a regex hint (`REFERRAL_MENTION_RE`) raising recall the same way. `upsertApplication()` resolves that name to an existing Contact by fuzzy name match (`findContactByName()`) and sets `applications.referred_by_id` — but only if the application doesn't already have one, so a later email can never silently overwrite a manually-corrected referrer. This reverses the prior behavior/limitation documented below.

**Calendar invites ≠ interviews (fixed 2026-10-16):** an attached `.ics` used to force `type = INTERVIEW_INVITE`, so a networking call sent as a plain Google Calendar invite ("Alex and Jane", Meet link) moved the application to Phone Screen and got an "Interview — X" event. Now Claude alone decides the type, guided by `INTERVIEW_VS_NETWORKING` (a shared prompt block, duplicated in `scripts/email-pipeline.js` and `app/api/_lib/emailPipeline.js` — keep them in sync): interview = recruiter/coordinator/ATS/scheduling-tool sender or explicit interview wording; a 1:1 with an employee, coffee chat, informational interview or two-names invite = `NEW_CONTACT`/`FOLLOW_UP_NEEDED`; when unsure, networking. The invite only supplies timing for a real interview, and non-interview types get `interview_date = null`. `createCalendarEvent()` is skipped when an invite is attached (Google already puts the invite on the calendar; our copy duplicated it once per "event updated" email), skips a same-title event already on that day, and caps duration at 10h. **ICS gotcha:** Google/Outlook invites put a `VTIMEZONE` block *before* the `VEVENT`, and its `DAYLIGHT`/`STANDARD` rules have their own `DTSTART` (`19700308T020000`); `extractCalendarInvite()` now reads fields only from the `VEVENT` block. Reading the first `DTSTART` in the file made an event that started in 1970 and ran to the real end time, which Google shows as an all-day bar on every day. `parseIcsDate` also accepts `VALUE=DATE` (all-day) values now.

**Ported to Supabase (2026-08-01)** — writes directly to this app's live Postgres tables via raw PostgREST calls (`UrlFetchApp`, no npm available in Apps Script) using the service-role key, the same server-side trust model `api/_lib/supabaseAdmin.js` uses for the Vercel proxies. Since Apps Script has no session to derive a user from (unlike every other server-side call site, which uses `requireUser(req)`), `RECRUITING_USER_ID` is a single hardcoded user id included explicitly on every query/insert — this script serves exactly one recruiting-os account, not a multi-tenant signup flow. One deliberate behavior change from the old Notion version: contact `status` is only set on **create**, not overwritten on every re-processed email, so an automated run can no longer silently clobber a status you changed manually in the UI.

Cost: ~$0.001/email with Haiku (classification only runs once per thread-update, not per logged message) — the broader inbox keyword search increases how many threads get *scanned*, not how many get *classified* twice; each thread's Haiku call still only runs once per new message via the existing `msgcount_<threadId>` tracking.

### Push reminders — ntfy.sh (shipped 2026-09-17)

The pipeline can push a real phone notification instead of relying on you to notice something in the app or your inbox — deliberately not another email, since the whole point is cutting through the inbox this script already reads. Uses [ntfy.sh](https://ntfy.sh), a free public push-notification relay: `sendPush()` POSTs to `https://ntfy.sh/<NTFY_TOPIC>` and anything subscribed to that topic (the ntfy phone app, or the web app) gets a native push. Entirely optional — `NTFY_TOPIC` unset means `sendPush()` no-ops and everything else keeps working; there's no paid tier, phone number, or account involved.

- **Immediate, on classification** (`notifyStatusChange()`, called right after `upsertApplication()`): `OA_INVITE` (priority `high`, includes due date/link if known), `INTERVIEW_INVITE` (`high`), `OFFER` (`urgent`), `REJECTION` (`default`). Deliberately not `APPLICATION_CONFIRMATION`/`REPLY` — those are routine enough to just show up in the app rather than interrupt you.
- **Daily digest** (`checkOaDeadlines()`, its own time-driven trigger — separate from the every-10-minutes `processRecruitingEmails`, since it reads current application state rather than new email): one push listing every open, incomplete OA due within 3 days or already overdue, `urgent` priority if anything's due today/tomorrow/overdue else `high`. Re-sends daily until the OA is marked completed or its due date moves out of the window — that's intentional nagging, not a bug.
- **Setup**: install the ntfy app (iOS/Android) or use `https://ntfy.sh/app`, pick a long random topic string and subscribe to it, set `NTFY_TOPIC` to that string in Script Properties, then add a second trigger (`checkOaDeadlines`, Day timer) alongside the existing 10-minute one. `testPush()`/`runOaCheckNow()` are manual-run helpers for verifying the wiring. See the setup comment at the top of `scripts/email-pipeline.js` for the full walkthrough.
- **Script Properties past 50 are UI-read-only** (Google's own project-settings page caps the manual add/edit list at 50 — this pipeline alone accumulates one past that from `msgcount_<threadId>` tracking keys, one per processed thread) — past that cap, set a property by running a one-off `PropertiesService.getScriptProperties().setProperty(...)` call directly in the Apps Script editor instead (this is how `NTFY_TOPIC` actually got set — see git history for the exact throwaway snippet used, never committed since it'd have carried the real topic string). This is a display-only Google limit, not a quota — nothing else about the property is capped.
- **`UrlFetchApp` intermittently fails against ntfy.sh specifically** with `Address unavailable`, even though ntfy.sh itself responds in well under a second from anywhere else (confirmed via a direct `curl` during setup) — a known, reported Apps Script flakiness against Cloudflare-fronted origins, the same class of issue as the `events.umich.edu` Cloudflare challenge documented under Ingestion above. `sendPush()` retries up to 3 times with a 1.5s delay before giving up (`PUSH_RETRY_ATTEMPTS`/`PUSH_RETRY_DELAY_MS`) — fixed and **verified live** 2026-09-17 (failed on first attempt in production, succeeded on retry).
- **Verified live end-to-end 2026-09-17**: `testPush()` delivered to the real device after the retry fix, confirming the full chain (Script Properties → `UrlFetchApp` → ntfy.sh → phone app) actually works, not just that the code runs without throwing.

### Drafted replies (server scan only, v1.4 spec 10)

`app/api/_lib/emailPipeline.js` drafts a reply whenever it classifies a thread whose newest message is a person waiting on the user. Spec: `.planning/v1.4-useful-and-lean/10-reply-drafts.md`.

- **Gate** (`shouldDraftReply` in `api/_lib/replyDraft.js`). The classifier must return `needs_reply: true` and `personal` not false. Receipts, OA invites, OA completions and rejections are never drafted. Neither is a newest message from the user, an automated sender (`isAutomatedSender`), or bulk mail. The message must be at most 7 days old, so the 45-day first pass doesn't spray drafts. `user_settings.auto_draft_replies !== false`, and there's a cap of 8 per mailbox per run (it's the user's key).
- **Call times.** When `reply_intent` is `schedule_call` and `user_settings.availability` is set, `slotsFor` merges Google `freeBusy` across every connected calendar slot and `suggestSlots` (`src/lib/availability.js`, pure) picks 3 free slots: at least 18h out, inside the stated hours and zone, on different days. Without availability, the draft asks the other person for times instead of inventing any. Without a calendar, the slots come from the stated hours alone, and `slots_checked = false` says so in the UI.
- **Draft.** `draftReply` runs on the standard tier, using the last 3 messages with quoted history stripped, the classifier summary, the profile, and up to 3k chars of `profiles.resume_text`. It's written to `email_drafts` with ignore-duplicates, so a draft the user dismissed or finished never comes back. A newer message in the thread dismisses the older pending draft.
- **Settling.** When the user replies themselves (the thread's newest message is theirs), the next scan marks that thread's pending drafts `done`.
- **Never sends.** Inbox shows the draft under the thread (edit, Copy, "Copy & open in Gmail", Dismiss), and Today lists them under "Replies Drafted". The Apps Script pipeline doesn't draft, so its prompt needs no `needs_reply`/`reply_intent` mirror.
