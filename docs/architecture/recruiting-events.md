## Recruiting Events (v1.1 milestone, in progress since 2026-09-13)

Career fairs / info sessions / coffee chats and their multi-step registration ladders. **All phases (8–15) built as of 2026-10-16.** The live Google round-trip for the Recruiting calendar is still owed (needs the user's re-consent — see `.planning/v1.1-HANDOFF.md`'s manual steps). Phase list in `.planning/ROADMAP.md` (v1.1 section). Executed directly, no GSD orchestration — do not re-introduce it.

**Tenancy — the repo's first shared data (`supabase/migrations/20260913000000_recruiting_events.sql`):** `schools`, `employers`, `events`, `event_attributes`, `event_requirements`, `ingest_sources` are readable by any authenticated user whose `profiles.school_id` matches (via `current_user_school_id()`, a `security definer stable` helper so the policy doesn't recurse through `profiles`' RLS per row) and have **zero client-facing write policies** — only service-role handlers in `api/` write them. `user_events` / `user_event_relevance` / `user_event_requirement_completions` are ordinary `auth.uid() = user_id` overlays; one user's status, notes and completions are invisible to everyone else, including via `count`. `profiles.school_id`, `contacts.employer_id`, `applications.employer_id` are nullable resolver columns **alongside** the free-text fields — never migrate `company`/`school` in place (Coverage/Discover/Explore/job-board dedup/email pipeline all key off the text via `normalizeCompanyName`; `lib/employers.js` wraps it, lookup-only). The signup trigger resolves `school_id` from the email domain; existing users pick a campus in Settings (datalist over `schools`). `app/test/rls.test.js` proves cross-school + cross-user isolation through anon-key JWTs against whatever project `.env` points at — run it after any policy change.

**Tests:** `cd app && npm test` (vitest; `vitest.config.js` loads the root `.env`). Pure suites cover requirement gating (`lib/eventRequirements.js` — `confirmed` is never legal until every required step has `completed_at`), the ingest primitives, the Localist adapter against a real captured feed (`test/fixtures/umich-3172.json`), dedup, freshness and tz.

**Ingestion (`api/_lib/eventsIngest.js`, `api/events-ingest.js`, `src/lib/useEventIngest.js`):** one adapter per *platform* (`src/lib/ingest/adapters/`), parameterized per school by `schools.feed_config.sources[]` — adding a campus is a config row. `localist` understands both UMich's `/group/<id>/json?v=2` flat shape (local wall-clock + `time_zone`) and standard Localist API v2; `careerfairplus`/`handshake`/`twelvetwenty`/`symplicity` are stubs by design (SSO-gated → paste-import in Phase 13, never scraped). **Fetch path gotcha:** `events.umich.edu` sits behind Cloudflare and challenges non-browser TLS *probabilistically* — Node fetch from this Mac was challenged on some runs and passed on others. So `mode:'run'` tries a server-side fetch and, on a challenge, returns `needsRelay`; the hook (mounted in `AppInner`, daily gate per browser) fetches the CORS-open JSON from the real browser and POSTs it back as `mode:'relay'`. Relayed payloads are untrusted: every item's permalink host must equal the configured feed host (403-style 400 otherwise), then the **freshness gate** (`lib/ingest/freshness.js` — >50% of items older than 45d, or nothing inside a configured term window ⇒ source marked `degraded_at`/`degraded_reason`, **nothing written**; a good pull clears it), then within-batch dedup, employer upsert ("Career Cafe featuring X"), and per-item upsert by `(source_kind, source_ref)` / near-duplicate merge (`lib/ingest/dedup.js`: ±60 min, title Jaccard ≥ 0.8, employer must agree when both known) / insert. School-wide cooldown 12h on `ingest_sources.last_run_at`; `INGEST` rate tier 10/60s. The partial unique index `(school_id, dedup_key) where shared and not archived` is the hard backstop — it can't be named in `ON CONFLICT` via PostgREST, so the writer catches `23505` row-by-row and counts it as a merge. CSP `connect-src` allows `https://*.edu https://*.localist.com` for the browser relay (and `style-src`/`font-src` now allow Google Fonts — a pre-existing CSP bug had production on fallback fonts).

**Enrichment + relevance (Phase 10):** attributes/requirements/registration deadlines are extracted **once per event** — the client runs the AI call through `lib/ai.js` with its own BYOK key (`lib/eventEnrichment.js`, 6 events per `MINI` call, prompt exported as `ATTRIBUTES_PROMPT_HEADER`; registration deadlines reuse `lib/deadlines.js`'s Exa-`/contents`→AI path via the new `extractStatedDeadlines(items, { subject: 'registration' })`, which `extractDeadlines(jobs)` now wraps) and commits through `api/events-enrich.js` → `api/_lib/eventsEnrich.js`, which whitelists/enum-checks/length-caps every field, requires every event id to belong to the caller's school (403 otherwise), and **upserts requirements by `(event_id, step_order)` without ever deleting** so a user's completion rows survive re-extraction. `event_attributes.content_hash` is what makes it once-per-event across users; `raw.deadlineCheckedAt` throttles page re-reads to weekly. `lib/eventRelevance.js` is the pure per-user scorer (employer signals: target/applied/known-contact; role fit vs `profile.focus`; kind; timing; stale >14d ⇒ tier capped at medium — "the scorer won't upgrade it"); `computeRelevance` only emits writes whose `inputHash` changed, and `effectiveTier` honours `overrideTier`/`dismissedAt`. `lib/attention.js` gained `eventRequirementsDue`, `registrationClosingSoon`, `eventFollowUpsOverdue`, `degradedEventSources` — Today renders them, no second action queue. `lib/useRecruitingEvents.js` (mounted in `AppInner` as `eventPool`, `enabled` only with a `school_id`) is the one hook the UI consumes: loads pool + overlay, runs the enrichment pass once per browser-day when anything needs it, persists changed relevance rows, and exposes `setStatus` (gated by `canSetStatus`), `toggleRequirement`, `setOverride`, `dismiss`.

**Calendar extension (Phase 11):** pushes go to a dedicated **"Recruiting" calendar the app creates, never primary** (`googleCalendar.js`'s `ensureRecruitingCalendar(slot)` — id cached in `user_settings` under `recruiting_calendar_id:<slot>`, verified against `calendarList` each session). That needs the `calendar.app.created` scope (non-sensitive; verified via Google's reference that it covers `calendars.insert`, `calendarList`, and event insert/patch/delete on app-created calendars; `freeBusy` already works under `calendar.events`) — `api/_lib/googleOAuth.js` now requests it, the callback stores Google's granted `scope` string in `google_calendar_tokens.scopes`, and `GET /api/google-connect` reports `canManageCalendars`. **Grants made before this scope existed keep working for everything else but can't reach the Recruiting calendar until the slot is reconnected** — Settings shows a "⚠ Reconnect" nudge when the sync-owner slot lacks it. The proxy allowlist is now an explicit set in `api/_lib/calendarAllowlist.js` (events on any calendar id, `calendarList` GET, `calendars` POST, `freeBusy` POST; never calendar delete/ACL/settings), still checked before the token lookup, with a test table. `updateEvent` is PATCH; under `singleEvents=true` list ids are per-occurrence, so patching/deleting an id touches that instance only — `normalizeEvent` now surfaces `recurringEventId` so callers never confuse the two. `lib/eventCalendarSync.js`: `pushEvent` (main event + one reminder per incomplete required step with a `due_at` + one for `followup_due_at`, all tagged `extendedProperties.private.recruitingOs`; ids in `user_events.calendar_event_id` / `calendar_reminder_ids`), `unpushEvent` (in-app delete → Google delete, 404/410 tolerated), `reconcile` (Google-side delete → **null the id, keep the row**), and `calendar_sync_hash` so daily feed re-verification doesn't re-PATCH unchanged events. `lib/useEventCalendarSync.js` (mounted in `AppInner`) auto-pushes relevance-high events (≤8 per run), reconciles once per session, and reads `user_settings.recruiting_calendar_sync` `{ enabled, slot }` (default personal). **CR-02 fixed**: `CalendarTab` refreshes the Feed cache on create/delete.

**Conflict engine (Phase 12, `lib/conflicts.js`, tests written first):** `freeFragments({ window, blocks, transitBufferMin, minFragmentMin, timeZone, overrides, excludeIds, excludeEventId })` subtracts calendar blocks from an event window and returns usable fragments — the brief's canonical case (10:00–16:00 fair vs 12:00–13:30 + 16:00–17:30 class, 15-min transit) yields `10:00–11:45, 13:45–15:45`. Timed blocks are **hard** by default; all-day blocks default **soft** (an all-day marker would otherwise zero every fragment that day — deliberate deviation from "default hard", override is one click); `block.soft` and per-block `user_events.block_overrides` (`{ [blockId]: 'soft'|'hard' }`) win. Soft blocks never remove time but come back as `softOverlaps` with minutes. A hard block just outside the window still applies its transit buffer (a class starting as the fair ends means leaving early). All math is epoch-ms so mixed offsets are fine; all-day dates are interpreted in `timeZone` via `lib/ingest/tz.js` (Google's end date exclusive). `conflictsForEvent(event, listEventsOutput, { userEvent, school })` is the app-shape glue (excludes the pushed event + its reminders, uses `schools.transit_buffer_min`) and returns `{ fragments, summary: 'Free 10:00–11:45, …' | 'No conflicts' | 'No usable window', softOverlaps, … }`.

**Contributed events — paste / CSV / ICS / manual (Phase 13):** the SSO-gated platforms (Handshake, Career Fair Plus, 12twenty, Symplicity) enter the pool through `components/EventImportModal.jsx` (Calendar → "Import events"; Phase 14 re-houses it in the Events view) — the student pastes what they can already see, nothing scrapes an authenticated session. `lib/eventImport.js`: `extractFromPaste` (one `AI_MODELS.STANDARD` call via `lib/ai.js`, model-reported confidence), `parseIcs` (folding, `TZID`, `VALUE=DATE`, Zulu), `parseCsv` (header aliases, quoted cells, tabs), `manualDraft` (confidence 1). Drafts are staged in the modal (editable, functional `setDrafts`), annotated by `lib/ingest/contribute.js`'s `annotateDuplicates` (same `findNearDuplicate` as ingestion) and `gateVisibility`, then committed via `api/events-contribute.js` → `api/_lib/eventsContribute.js`, which is **the poisoning boundary**: re-validates every field (`validateContribution`), dedups against the school's shared pool + the caller's own private rows (a twin **merges** — re-verifies the existing row, fills missing `registration_url`/`url` — never a second row; results come back in input order), and only lets confidence ≥ `SHARE_CONFIDENCE` (0.8) become `visibility='shared'` — everything else is `private` to `contributed_by` until `{ promote: eventId }` (same dedup + gate; a twin found at promote time archives the private row). `{ remove: eventId }` deletes only the caller's own private rows; shared rows are never user-deletable. Stated requirements in a paste land in `event_requirements`. Verified live both via the server lib (shared / private / merged / rejected / cross-user refusals) and through the real modal → HTTP path (a manual 11:05 twin of the ingested 11:00 AbbVie cafe merged). `normalizeTitle` now drops 1-char tokens ("Q&A" noise) so "X Info Session" matches "X Info Session + Q&A". The `useStagedIngest` generalization planned for this phase was not built — the modal's local staged state covers it and nothing else needs the persisted-pending shape.

Today renders four sections from `components/today/EventAttentionSections.jsx` (Signup Steps Due, Registration Closing — hidden for an event whose unfinished required `register` step already shows above —, Event Follow-Ups Overdue, Event Feeds Degraded) right after the OA sections. `/demo` now includes Calendar: `DemoApp` mounts `useRecruitingEvents({ isDemo: true })` over `demoData.js`'s seeded events, and `googleCalendar.js` returns `[]` from `listEvents` / throws a friendly error on writes when the path is `/demo`.
