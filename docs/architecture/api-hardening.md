# API hardening

> Moved out of CLAUDE.md on 2026-10-16 (v1.3 spec 07). Dated "shipped" notes are history; check the code before trusting a detail.

## API Hardening — rate limiting, security headers, path allowlisting (shipped 2026-08-10)

A security pass prompted by researching common "vibe-coded app" failure modes (missing rate limits, over-permissive proxies, missing security headers, unvalidated uploads — the five most common OWASP-flavored gaps in AI-assisted codebases per current industry write-ups). BYOK encryption, RLS, and `requireUser()` auth gates (see Multi-Tenant Auth + BYOK above) already covered the biggest risks; this closes the remaining gaps found by a targeted audit.

- **Per-user rate limiting (`api/_lib/rateLimit.js`)**: every proxy/CRUD endpoint (`claude-api`, `openai`, `exa`, `gh-api`, `google-calendar`, `keys`, `google-connect`) now calls `checkRateLimit(user.id, TIER)` right after `requireUser()` and 429s (with `Retry-After`) if exceeded. Backed by Upstash Redis (`@upstash/ratelimit` sliding window), provisioned via `vercel integration add upstash` → "Upstash for Redis". **Reads `KV_REST_API_URL`/`KV_REST_API_TOKEN`** (falls back to raw `UPSTASH_REDIS_REST_URL`/`TOKEN` if ever present) — the Marketplace integration injects the legacy `@vercel/kv`-compatible names, not the raw Upstash ones its own docs show; confirmed against this project's actual `vercel env ls` output. **Fails open (no-op) if neither pair is set**, so local dev and any environment that hasn't provisioned Redis yet still work; this is a defense-in-depth layer against cost/abuse (a leaked BYOK key or a client-side retry-loop bug burning unbounded Anthropic/OpenAI/Exa spend), not an auth gate. Tiers: `AI`/`SEARCH` 30 req/60s, `GITHUB`/`CALENDAR` 60 req/60s, `CRUD` (key management) 20 req/60s.
  - **Provisioned and verified live in production 2026-08-11**: signed up a disposable test account (`enable_confirmations = false` in `supabase/config.toml` means no email-click needed) against `https://recruiting-os-phi.vercel.app`, hammered `/exa/search` with 40 concurrent requests — got 28×400 (correctly past the limiter, failing only on missing BYOK key) + 12×429 with `Retry-After` populated, exactly matching the 30/60s `SEARCH` tier. Rate limiting is live, not just wired.
  - Local dev still needs the two vars copied from `app/.env.local` (written by `vercel env pull`) into the root `.env` that `vite.config.js` actually reads from — Claude Code's own permission settings block reading/writing `.env*` files directly, so this one step has to be done by hand: `cd app && grep -E '^(KV_REST_API_URL|KV_REST_API_TOKEN)=' .env.local >> ../.env`.
- **Path allowlisting** on the 5 `?path=`-passthrough proxies (`claude-api`, `openai`, `exa`, `gh-api`, `google-calendar`) — previously any authenticated user could hit *any* endpoint on api.anthropic.com/api.openai.com/api.github.com/googleapis.com through the app, not just the intended ones (host couldn't be hijacked since it's string-concatenated not resolved from `path`, but there was no defense-in-depth). Each proxy now 403s any `path` outside its actual usage: `claude-api` → `v1/messages` only; `openai` → `v1/chat/completions` only; `exa` → `search`/`findSimilar`/`contents` only; `gh-api` → `repos/*`/`users/*`/`orgs/*` only; `google-calendar` → `calendar/v3/calendars/primary/events*` only. **Path check runs before the BYOK-key/refresh-token lookup** in every proxy (not after, as first written) — fails fast on a bad path without an unnecessary DB round-trip, and matters for testability too: with the check after the key lookup, a user with no BYOK key got the same 400 for both allowed and disallowed paths, masking whether the allowlist was doing anything. Verified live in production: bad paths on `exa`/`claude-api`/`gh-api` all 403, `gh-api/repos/vercel/next.js` (allowed shape) returned a real 200 from GitHub.
- **Security headers (`vercel.json`)**: added a `headers` block — `Content-Security-Policy` (default-src 'self', connect-src allows `https://*.supabase.co`, frame-ancestors 'none'), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`. Closes a clickjacking gap (app could previously be iframed and UI-redressed into triggering real actions — delete BYOK key, create calendar event, etc.). Vercel-only (`vercel.json` isn't read by the Vite dev server), so local dev is unaffected.
- **`AddToCalendarModal.jsx` upload guard**: `accept="image/*"` was UI-only (no server- or client-side enforcement) and `downscaleImage()`'s promise rejection was unhandled. Now checks `file.type`/`file.size` (20MB ceiling) before decode and catches decode failures into the existing error banner — low severity (the canvas re-encode already bounded what actually reached Claude vision), but removes an unhandled-rejection footgun.
- **Audited and confirmed already fine, no changes needed**: BYOK keys/service-role key never reach the client bundle; `user_api_keys`/`google_calendar_tokens` RLS is correctly default-deny (zero policies); all DB access goes through supabase-js's query builder (no raw SQL / injection surface); no `dangerouslySetInnerHTML` or unsafe `innerHTML` anywhere in `app/src`; CSRF isn't a meaningful risk (Bearer-JWT auth, not cookies); Google OAuth state/PKCE is handled by `supabase-js` itself, not custom code; no secrets ever hit `console.log`/`console.error` in `api/*.js`; `npm audit --production` is clean (0 vulnerabilities — the 4 found by a full `npm audit` are all pre-existing **dev-only** tooling, `vite`/`esbuild`/`postcss`/`nanoid`, not shipped to production or the client bundle, and not introduced by this pass).
