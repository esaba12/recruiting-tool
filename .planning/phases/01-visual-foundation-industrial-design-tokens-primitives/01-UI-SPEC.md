# Phase 1 — UI Design Contract

> Visual and interaction contract for the industrial/control-panel token-VALUE reskin. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Aesthetic direction (explicit, per global frontend-aesthetics directive):** Industrial / control-panel. Locked by PROJECT.md. Concretely: a cool gunmetal/graphite neutral scale (not the current warm-paper charcoal), a punchy safety-orange/signal-amber accent (not a soft pastel orange), and indicator-light-saturated success/warning/danger hues — evoking dense instrument panels and dark-IDE-theme conventions (Nord/Monokai-adjacent chroma, not literal brand copy of either), rendered here as a **light-canvas UI** (the existing dark-sidebar-only pattern is preserved, not expanded into app-wide dark mode this phase). Every value below was run through the `dataviz` skill's validator before being locked — see Color section for the actual pass/fail output, not an eyeballed choice.

**Hard constraint honored:** token *names* (`ink`, `accent`, `success`, `warning`, `danger`, plus the pre-existing `canvas`) are unchanged. Only hex values change, inside `app/src/index.css`'s existing `@theme` block. No new token family is introduced. Zero call-site edits outside `app/src/index.css`, `app/src/components/ui/*`, and `app/src/shared.jsx` (the last one only for the off-token color fixes below — see Open Questions Resolved).

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn deliberately NOT initialized this phase |
| Preset | not applicable |
| Component library | none (hand-rolled `ui/` primitives: Button, Badge, Card, Tabs, Input, Select, Modal, EmptyState, ChipToggleGroup) |
| Icon library | lucide-react (unchanged — icon `size`/`strokeWidth` props already parameterized, no icon swap this phase) |
| Font | Space Grotesk (headings, unchanged) / Public Sans (body, unchanged) / IBM Plex Mono (data — rolled out systematically this phase, see Typography) |

**Why shadcn was not initialized:** `components.json` doesn't exist in this repo, and RESEARCH.md's Standard Stack section is explicit: "No new libraries required. This phase re-weights the already-installed stack." The project's hard constraint (same token names, new values, zero call-site edits) is fundamentally incompatible with swapping the styling layer to a shadcn preset mid-milestone — that would touch every one of the ~50 files consuming `ink-*`/`accent-*` classes today, not zero of them. Initializing shadcn is out of scope for this phase and this milestone; the existing hand-rolled `ui/` primitives are the correct target for a value-only reskin.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing |
| md | 16px | Default element spacing |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

**Exceptions:** the 8 `ui/` primitives currently use several non-4px-multiple Tailwind spacing utilities as internal chrome padding (`px-2.5`=10px, `py-1.5`=6px, `px-3`=12px paired with `py-1.5`=6px, in `Button.jsx`/`Input.jsx`/`Select.jsx`/`Tabs.jsx`). **These stay unchanged this phase** — resizing component chrome density is a layout decision distinct from "token values + typography + palette," and is out of this phase's stated success criteria (a spacing-scale cleanup, if wanted, belongs in Phase 7's full per-screen sweep, alongside the other layout-level decisions that phase already owns). Do not silently round these to the 4px scale as a drive-by change; if the executor notices this, it's a legitimate future-phase note, not a Phase 1 blocker.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (Input/Select/EmptyState text) | 14px (`text-sm`) | 400 (regular, Public Sans) | 1.5 |
| Label (Badge, Tabs, Input/Select `<label>`) | 12px (`text-xs`) | 600 (semibold, up from current 500/medium — see below) | 1.4 |
| Heading (h1/h2/h3, global) | inherits existing per-component `text-*` size | 600 (semibold, Space Grotesk — unchanged, already the global default) | 1.2 |
| Data / Mono (dense table & panel fields — dates, counts, deadlines, status codes) | 12–13px, `tabular-nums` | 500 (medium, IBM Plex Mono) | 1.4 |

**Two weights, declared exactly:** 400 (regular — body copy, EmptyState messages) and 600 (semibold — headings, Badge/Tabs/Button labels, and the new mono data treatment at 500 sits as the one deliberate typographic exception, justified below). Do not introduce a third weight (e.g. no `font-bold`/700 anywhere in the 8 primitives).

**Button label weight bump (500 → 600):** `Button.jsx`'s current `font-medium` (500) becomes `font-semibold` (600) as part of this phase. Two reasons: (1) it's the correct "chunky, stenciled control-panel label" look for the industrial direction — thin CTA labels read as generic-SaaS, not instrument-panel; (2) it gives the primary Button variant's white-on-`accent-600` text a legitimate WCAG large-bold-text safety margin on top of the 4.59:1 ratio already computed for that pair (see Color section) — belt-and-suspenders, not a substitute for the ratio fix.

**IBM Plex Mono rollout — exact scope (VIS-02):** introduce one new shared primitive, `app/src/components/ui/Mono.jsx`:
```jsx
import { cn } from '../../lib/cn.js'
export default function Mono({ className, children }) {
  return <span className={cn('font-mono tabular-nums', className)}>{children}</span>
}
```
Wrap dense, multi-row/multi-field values in `<Mono>`: table date columns (`ContactsTable.jsx`'s "Last"/"Follow-Up"), Pipeline stage-age/deadline countdowns, Job Boards' posting-date/deadline badges, status codes in dense list rows. **Do not** wrap large single-hero-number displays (e.g. `ApplicationDetailModal.jsx`'s duplicate-count display, which correctly stays on `font-heading` + `tabular-nums` per its existing treatment) — that's a headline-stat role, not a dense-data role, and blurring the two collapses the visual hierarchy VIS-02 is trying to establish (per RESEARCH.md Pitfall 4). `fmt()` in `shared.jsx` stays a plain string function; `<Mono>{fmt(v)}</Mono>` is the call-site pattern, not a change inside `fmt()` itself.

## Color

Full commands and results are in "Validation Evidence" below. Two pre-existing, previously-unvalidated contrast failures were found and fixed as part of choosing these values (not introduced by this phase) — see "Fixes beyond the reskin."

### Fixes beyond the reskin (found while validating — do these, not just the hue swap)

1. **`Button.jsx` primary variant must move from `accent-500` to `accent-600`** as its default background (hover moves to `accent-700`). The *original* `bg-accent-500` + white text combination measured **2.23:1** against the old accent-500 hex — a pre-existing WCAG failure, not something this reskin introduces. The new `accent-600` (`#c94e0a`) + white measures **4.59:1**, clearing the 4.5:1 normal-text floor. `accent-500` itself stays reserved for borders/icons/rings/dark-text-on-light-badge contexts where white-text-on-solid isn't the pairing.
2. **`shared.jsx`'s `URGENCY_COLOR.MED` must move from `bg-warning-400` to `bg-warning-600`** (white text). The original `warning-400` + white measured **1.91:1** — a severe pre-existing failure on a real UI element (the urgency pill shown on every MED-urgency contact). New `warning-600` (`#9c690d`) + white measures **4.73:1**.
3. **`shared.jsx`'s `URGENCY_COLOR.LOW` and `REFERRAL_STATUS_COLOR['Not Asked']` must use `text-ink-500` (not `text-ink-400`)** against their `bg-ink-100` background. `ink-400` vs `ink-100` measures 4.12:1 (fails 4.5 for small `text-xs` labels); `ink-500` vs `ink-100` measures 5.85:1.

None of these are visually jarring departures — they're one ramp-step darker than the original intent — but they must be applied exactly, not approximated, or VIS-03 doesn't actually hold for these three real UI elements.

## Open Questions Resolved

**1. Off-token `shared.jsx` badge-color entries (Champion/Technical/Onsite/LinkedIn/Meeting) — remap onto the existing 5 token families, do NOT add a 6th/7th family.** The hard constraint locks the token family set to `ink`/`accent`/`success`/`warning`/`danger`; introducing a new family is schema-change territory this phase explicitly rules out. Exact remap (apply in `shared.jsx`, replacing every `orange-`/`purple-` literal):

| Map | Entry | Old (off-token) | New |
|-----|-------|------------------|-----|
| `STATUS_COLOR` | `⭐ Champion` | `bg-orange-100 text-orange-800` | `bg-accent-100 text-accent-800` |
| `STAGE_COLOR` | `Technical` | `bg-orange-100 text-orange-800` | `bg-warning-200 text-warning-800` |
| `STAGE_COLOR` | `Onsite` | `bg-purple-100 text-purple-800` | `bg-warning-600 text-white` |
| `TYPE_COLOR` | `LinkedIn` | `bg-purple-100 text-purple-700` | `bg-warning-800 text-warning-100`† |
| `TYPE_COLOR` | `Meeting` | `bg-orange-100 text-orange-700` | `bg-ink-200 text-ink-700` |

† Corrected direction from the initial `warning-700`/`warning-100` sketch (4.25:1, fails) to the validated `warning-800`/`warning-100` pairing (6.22:1, matches the Cooling/Phone-Screen/Asked badges' existing pattern) — use this exact class pair, not the lighter one.

Rationale for the specific assignments: `Champion`→`accent` reads as "this app's single best-tier signal," consistent with accent already being reserved for top-priority/primary elements. `Technical`/`Onsite` ramp deeper into `warning` (Phone Screen is already `warning-100`) so the three interview stages read as one graduated "getting more serious" sequence rather than three unrelated hues — `Onsite` steps all the way to a solid `warning-600` fill (last interview stage before Offer) to visually separate it from Phone Screen/Technical's lighter fills. `LinkedIn`/`Meeting` fill the two remaining unused shades (`warning`'s dark end, and a second `ink` step distinct from `Other`'s `ink-100`) since `accent`/`success`/`ink-100` are already spoken for by `Email`/`Call`/`Other` in the same map.

**2. `charts/theme.js` hex-mirror sync — DEFERRED to Phase 7, documented explicitly (not a silent gap).** Per ARCHITECTURE.md's Suggested Build Order and this phase's own stated success criteria (which name the 8 `ui/` primitives + `shared.jsx`'s badge maps, not the charts directory), `charts/theme.js`'s `STATUS_CHART_COLORS`/`CHART_SERIES`/`CHART_GRID`/`CHART_AXIS_TEXT`/`CHART_SURFACE`/graph-dark-mode hex literals **stay on the current values through this phase.** Known, accepted, temporary consequence: the Overview tab's "Network by Status" donut chart will visually disagree with the Network table's status badges for the same 5 semantic states until Phase 7 lands. This is tracked here explicitly so it is not mistaken for a Phase 1 regression when spotted in review — it is the deferred half of a decision this UI-SPEC makes on the record, not an oversight. The validated replacement hex values for `charts/theme.js` (`#2f8f3d`/`#d99a12`/`#b3312c`/`#f2680a`/`#666c74` for the 5 status slots, `#c94e0a` for `CHART_SERIES`) are already computed above and should be handed to Phase 7's plan directly rather than re-derived.

**3. Exact new hex/OKLCH values** — resolved above; every value passed the applicable `dataviz` check before being locked in.

## Copywriting Contract

This phase ships no new screens or user-facing copy strings — it is a token-value + primitive-styling + typography phase. The contract below documents what stays fixed vs. what visual treatment changes, so the checker isn't looking for new copy that doesn't exist:

| Element | Copy |
|---------|------|
| Primary CTA | No new CTA copy this phase. Existing Button label text is unchanged app-wide; only the primary variant's background (`accent-500`→`accent-600`) and label weight (500→600) change — see Typography/Color. |
| Empty state heading | No new copy. `EmptyState.jsx`'s existing `msg` prop values (set per call site elsewhere in the app) are unchanged; only the wrapper's typography (color/weight per the new `ink`/font contract) changes. |
| Empty state body | Same as above — no copy edits in scope. |
| Error state | No new error copy this phase (no new error-producing logic is introduced by a token/CSS change). Existing error banners keep their current `danger`-token styling, now rendering against the validated new `danger` ramp. |
| Destructive confirmation | Unchanged this phase — the existing native `confirm()` pattern (e.g. `DuplicatesPanel`'s "Archive N duplicates") and `Button variant="danger"` styling both carry forward; `danger-600`/`danger-700` are now WCAG-validated (8.17:1 / 10.81:1 with white text — comfortably clear, no fix needed here, this pair was never broken). |
