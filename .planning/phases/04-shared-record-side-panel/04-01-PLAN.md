## Resolved implementation decision — responsive dual-axis animation

04-RESEARCH.md Assumption A1 left this open: framer-motion cannot express different `initial`/`animate`/`exit` values per CSS breakpoint, and this codebase has no precedent for JS viewport detection (it uses Tailwind `md:` classes everywhere).

**Chosen: a `useMediaQuery('(min-width: 768px)')` hook selecting which transform object is spread onto one `motion.div`.**

Why not CSS-only Tailwind responsive transform classes, despite that being the house convention: the shell must animate *out* before unmounting. `AnimatePresence` is what gives `ui/Modal.jsx` that behavior today. A CSS-transition approach would need a hand-rolled "mounted" state flag to get an entrance transition at all (React paints the final class on first render), plus a hand-rolled unmount timeout for the exit — which is precisely the pattern 04-RESEARCH.md's "Don't Hand-Roll" table rejects. `useMediaQuery` is ~20 lines wrapping the native `window.matchMedia`, adds no dependency, and confines JS viewport detection to the single thing CSS cannot express here. All *static* responsive layout in `SidePanel.jsx` (width, corner radius, alignment, height) still uses Tailwind `md:` classes, matching the house convention; only the animated axis is JS-selected, and the hook's breakpoint (768px) is Tailwind's `md:` breakpoint so the two never disagree.
