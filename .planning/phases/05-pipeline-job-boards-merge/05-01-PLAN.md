## Hard constraints for this plan

1. **Neither body's internal logic changes** (D-02). The only permitted edits inside the two renamed files are the `export default function` identifier and, in the Applications body, its own top-of-component banner comment. Every other byte carries over. Both files stay in the directory they are in today, so no relative import path changes.
2. **Do not unify the two refresh prop names** (05-RESEARCH.md Pitfall 2). The Applications body destructures `onRefresh`; the Job Boards body destructures `onImported`. Both resolve to the same `load` function in `App.jsx`, but each body keeps its own name. Renaming either one silently hands a body `undefined`.
3. **Do not copy `apps` (or any prop) into shell-local state** (05-RESEARCH.md Pitfall 1). A stale snapshot means a job imported on the Job Boards view is missing from the Applications view until a full reload.
4. **Do not merge the two toolbars** (D-04) and do not lift either body's internal filter/search/bucket state into the shell.
5. **Do not touch `counts.pipeline`** (05-RESEARCH.md Pitfall 4). `activeApps` already includes newly imported Wishlist-stage rows; the badge needs no recalculation and none is requested.
6. **Do not render both views at once and hide one with CSS.** `jobBoards/RepoJobsView.jsx` runs auto-import and deadline-fetch effects that must not run while the user is looking at Applications. Mount exactly one body.
7. **`app/src/components/SettingsTab.jsx` is out of scope.** Its BYOK provider entry keyed on the string `github` is unrelated to the nav id being removed and must survive untouched.
8. **`app/src/lib/icons.js` is out of scope.** Its `NAV_ICON` map keeps its `github` key even though no nav item references it any more; the final nav-config cleanup belongs to Phase 6, and editing a file this plan otherwise does not touch is the kind of churn Phases 2 and 4 both learned to avoid. The shell imports its icons straight from `lucide-react`, exactly as `App.jsx` already does for the Network view switcher.

## Task ordering rationale

The three tasks are strictly sequential and each one ends on a tree that builds and runs. Task 1 renames the Job Boards body while its only consumer still renders it from its own tab. Task 2 renames the Applications body and drops the shell into the path `App.jsx` already imports, so the Pipeline destination gains the switcher while the standalone Job Boards tab is still live — a deliberate one-commit overlap, not a mistake. Task 3 removes the overlap.
