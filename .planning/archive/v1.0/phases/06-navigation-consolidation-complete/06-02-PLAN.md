## Hard constraints for this plan

1. **Do not touch the Grow deep-link relay** (`06-RESEARCH.md` Pitfall 3, `06-PATTERNS.md` "Untouched (verify-only)"). `goFindPeople`, the `growFocusCompany` state, and the plain conditional that mounts the Grow destination must come out of this plan byte-for-byte identical. Their unmount-on-tab-switch shape is the only reason a repeat "Find people" click on the same company re-triggers a fetch. Plan 06-03 gates on this with a byte-level diff.
2. **Do not convert any render branch to an always-mounted, CSS-hidden form.** This plan edits the same function that holds the Grow branch, which makes "clean up while you're in there" tempting. Every surviving branch keeps its exact current shape and its exact current position in the list.
3. **Settings must be reachable on mobile** (`06-RESEARCH.md` Pitfall 2). Removing the entry from the nav array removes it from the mobile bottom bar as well as the desktop rail, because both map the same array. The desktop footer button alone does not restore mobile access — the mobile floating-action stack needs its own button. Shipping only the desktop half is a regression on load-bearing functionality: no AI feature in this app works until a user has added BYOK keys in Settings.
4. **Do not add a new prop for Settings** (`06-RESEARCH.md` anti-patterns). `onTabChange` is already threaded from `App.jsx` through `AppShell.jsx` into `Sidebar.jsx`. The buttons call it directly.
5. **Do not add a new visibility boolean for Settings** (`06-RESEARCH.md` anti-patterns). Reuse the existing `hideQuickActions` gate. `AppShell.jsx` already sets it from `demoMode`, and demo mode genuinely has no Settings destination — a second boolean would only create drift risk.
6. **`app/src/components/SettingsTab.jsx` is out of scope** (D-02). Only how Settings is *reached* changes; the destination itself is untouched.
7. **`app/src/lib/icons.js` is out of scope.** Its nav-icon lookup map keeps its now-unreferenced key for the retired destination, exactly as it kept the one Phase 5 orphaned. That map is a lookup, not a nav config — nothing renders from its keys. Sweeping it belongs to Phase 7, and editing a file this plan otherwise does not touch is the churn Phases 2 and 4 both learned to avoid.
8. **Keep the network-view state declaration.** The setter for the Network destination's initial view loses its only caller when the retired branch goes, but the getter is still read and passed down. Leave the declaration and the prop pass-through alone: removing state that sits three lines from the deep-link relay buys nothing and risks constraint 1. Record it in the summary as a Phase 7 cleanup candidate.
9. **No visual invention.** Both new buttons copy class strings that already exist in `Sidebar.jsx` (`06-UI-SPEC.md` Color, Typography, Spacing). Specifically: the desktop button reuses the neutral footer-button fill rather than the amber accent, because the amber fill in that group is reserved for the single primary quick action; and it reuses the same 500-weight label as its four siblings rather than the locked 600 Label weight, because matching four adjacent siblings beats matching a table row — `06-UI-SPEC.md` flags this as inherited debt for Phase 7 and explicitly instructs against fixing it in isolation here.

## Task ordering rationale

Task 1 does all of the `Sidebar.jsx` work in one commit — the array shrink and both new buttons together — so there is never a commit where Settings has been removed from the nav but no replacement affordance exists. Task 2 does all of the `App.jsx` work plus the file deletion in one commit, because `06-RESEARCH.md` Pitfall 1 requires the tab-state default and the render-branch removal to land together or the app boots blank. Between the two tasks the tree builds and runs: the nav has lost its entry for the retired destination while that destination is still routed and still the default landing tab — visibly odd for one commit, structurally sound, and resolved by Task 2.
